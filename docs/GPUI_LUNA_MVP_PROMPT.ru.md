# Инструкция для GPT Luna: базовая оболочка iNtoo на GPUI

Этот файл можно целиком передать GPT Luna как задание на разработку. Он задаёт конечный объём MVP и последовательность применения доступных скиллов. Сейчас требуется реализовать основу; полный перенос iNtoo остаётся дальнейшим направлением развития.

## 1. Задание

Ты работаешь в репозитории iNtoo. Создай работающую базовую оболочку рабочего стола на Rust + GPUI с единым нейтральным оформлением, основными настройками и простым каркасом для добавления плагинов.

Работай небольшими завершёнными шагами. Не превращай задачу в разработку универсальной платформы. После выполнения критериев готовности заверши работу.

### Исходные данные

- Основная среда: Gentoo, Wayland, Niri.
- Существующая оболочка использует QML/Quickshell.
- Уже есть `prototypes/gpui-shell`: сначала изучи его код и используй рабочие части.
- Текущий iNtoo служит ориентиром для поведения, настроек и визуального языка.
- Сначала прочитай применимые `AGENTS.md`, `ARCHITECTURE.md`, `docs/GENTOO.md`, `prototypes/gpui-shell/README.md` и Cargo-манифест прототипа.
- Просмотри `docs/GPUI_MIGRATION.md`, `docs/GPUI_ACCEPTANCE.md` и существующие GPUI-контракты только в части текущей работы. Их более широкий план не расширяет этот MVP.
- Перед изменениями изучи `git status`: сохрани чужие незавершённые изменения.

### Технологические границы

- Весь новый интерфейс, включая настройки, запуск приложений и виджеты, реализуется на GPUI.
- Не используй QML, Qt, GTK, WebView или HTML/CSS для нового интерфейса.
- Системные библиотеки и протоколы Wayland, IPC, D-Bus и получения системных данных допустимы, когда нужны для функций MVP.
- Проверяй API по закреплённой версии GPUI и её исходникам. При необходимости используй официальную документацию. Не придумывай методы и возможности.
- Не обновляй GPUI ради удобства без конкретной необходимости. Не начинай крупный форк GPUI или собственный движок рендеринга.
- Недоступную обязательную возможность обозначь как блокер с конкретной причиной. Не подменяй shell-поверхности обычным окном и не объявляй задачу выполненной при отсутствии обязательной функции.
- Основные изменения делай внутри `prototypes/gpui-shell` и относящейся к нему документации. Обосновывай необходимость выхода за эти границы.
- Сохрани возможность запуска существующей QML-оболочки. В рамках MVP не меняй установленную сессию, автозапуск, установщик и зависимости системы.

## 2. Объём MVP

### Ядро и поверхности

- Запуск GPUI и создание необходимых Wayland shell-поверхностей.
- Фон рабочего стола, одна панель, открытие и закрытие запуска приложений и настроек.
- Общее состояние, конфигурация и тема без дублирования источников данных.
- Минимальная интеграция с Niri: получение рабочих столов и переключение между ними.
- Сохрани уже работающую поддержку мониторов прототипа. Зафиксируй фактическое поведение при подключении, отключении и изменении размеров выходов; недоработки явно перечисли.
- Не блокируй UI синхронными долгими операциями. Останавливай таймеры и подписки отключаемых модулей.

### Один базовый интерфейс

- Один аккуратный нейтральный стиль в духе iNtoo: читаемый текст, согласованные отступы, цвета, скругления и состояния элементов.
- Панель: рабочие столы, часы, кнопки открытия запуска приложений и настроек.
- Запуск приложений: список установленных приложений, поиск, запуск выбранного приложения.
- Используй корректную обработку desktop entries; не передавай строку пользовательского поиска в shell-команду. По возможности используй уже работающий механизм прототипа.
- Для интерактивных элементов обеспечь видимый фокус и базовую работу с клавиатурой. Escape закрывает временные панели.
- Не переноси одновременно Material ii, Waffle, Island и наборы их пресетов.
- Сложные эффекты, размытие, декоративные анимации и точное воспроизведение всех экранов не входят в MVP.

### Настройки

Нужен небольшой законченный экран со следующими рабочими параметрами:

- светлая и тёмная тема;
- акцентный цвет;
- размер текста и скругления;
- положение и размер панели;
- фон рабочего стола;
- включение, отключение и порядок модулей панели.

Изменения должны сохраняться между запусками и применяться сразу, где это возможно. Там, где действительно требуется перезапуск, покажи это пользователю.

Используй существующие ключи конфигурации, когда совпадает их смысл. Сохраняй неизвестные поля пользовательского JSON, проверяй диапазоны значений и не повреждай файл при ошибке записи. Для новых параметров задай значения по умолчанию. Используй временный конфиг для проверок. Не переноси всю схему QML в Rust и не добавляй отдельный независимый набор тех же настроек.

Не создавай переключатели, за которыми отсутствует действие. Ошибки чтения, сохранения и недоступные системные возможности должны иметь понятное представление в UI или диагностике.

### Каркас плагинов

Плагины MVP — модули Rust, подключаемые при сборке, с небольшим общим контрактом и явной регистрацией.

Контракт должен покрывать:

- стабильный идентификатор и название;
- создание и завершение работы;
- доступ к необходимым сервисам через небольшой контекст;
- собственные параметры с пространством имён;
- предоставление виджета панели и, при необходимости, элементов настроек;
- включение, отключение и порядок отображения.

Сначала найди существующие реестры и контракты прототипа. Расширь подходящий механизм либо кратко объясни, почему он не подходит. Не создавай параллельную систему с той же ответственностью.

Реализуй два встроенных плагина: часы и рабочие столы Niri. Они должны использовать общий контракт, а не существовать как специальные исключения в ядре. Кнопки основных настроек и запуска приложений могут остаться частью базовой панели.

При создании виджета каждый плагин получает в `PanelPluginContext::plugin_settings` только своё значение из `gpuiMvp.<plugin_id>`; отсутствующее пространство имён передаётся как `null`. Не читай настройки плагина напрямую из глобального состояния панели.

Добавь короткую инструкцию, как создать третий плагин: минимальный код, регистрация, конфигурация и запуск. Новому плагину допустимо требовать регистрации и пересборки, но не переписывания логики ядра.

Не реализуй динамические библиотеки, стабильный ABI, WASM, маркетплейс, песочницу, систему разрешений, горячую установку и универсальную шину событий. Не обещай изоляцию падений плагинов внутри одного процесса.

## 5. Критерии готовности

- [ ] Оболочка запускается документированной командой на целевой среде с необходимыми Wayland-протоколами.
- [ ] Панель и фон используют shell-поверхности, а весь новый интерфейс реализован на GPUI.
- [ ] Есть один согласованный базовый стиль.
- [ ] Работают поиск и запуск приложений.
- [ ] Настройки открываются, меняют поведение и сохраняются между запусками.
- [ ] Неизвестные поля пользовательского конфига сохраняются.
- [ ] Часы и рабочие столы подключены через общий контракт плагинов.
- [ ] Включение, отключение и порядок плагинов работают и сохраняются.
- [ ] Описано добавление третьего плагина; требование пересборки указано прямо.
- [ ] Существующая QML-оболочка остаётся доступной.
- [ ] Зафиксированы команды, фактические результаты проверок и ограничения живого тестирования.
- [ ] README отражает фактический объём, а MVP не назван полным переносом iNtoo.
